# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Personal portfolio: Astro 7 + React 19 + Tailwind 4 (via `@tailwindcss/vite`), pnpm, static output. Implements the "Signal" design (one-page, dark/light, EN/ES).

## Commands

- `pnpm dev` — dev server on :4321 (`astro dev --background` per AGENTS.md; manage with `astro dev status|logs|stop`)
- `pnpm build` / `pnpm preview`
- `pnpm lint` / `pnpm lint:fix` — ESLint flat config (`eslint.config.js`)
- `pnpm format` / `pnpm format:check` — Prettier (astro + tailwind class sorting plugins)
- `pnpm exec astro check` — type check; requires `typescript@6` (TS 7 breaks both `astro check` and typescript-eslint, so don't bump it)

No test suite.

## Architecture

- **i18n on one URL, switched without reload.** All copy lives in `src/i18n/content.ts` (`EN`/`ES` objects plus per-language arrays built by `build(isEs)`; ES is typed `typeof EN`, so add copy to both). `getContent()` in `src/i18n/index.ts` zips both languages: every string becomes a `Txt` (`string`, or `{ en, es }` when they differ). Render text with `<T v={...} />` (emits `<span lang="en">` + `<span lang="es">`; CSS in `global.css` hides the inactive one via `html[data-lang]`). Attributes (`aria-label`, `alt`, `title`) go through `{...attrs({ 'aria-label': txt })}`; string work on a `Txt` uses `pick`, `both`, `splitTxt`. Never render a `Txt` with `{x.foo}` directly (it prints `[object Object]`).
- **Preferences:** the inline script in `Layout.astro` sets `data-theme` and `data-lang` before paint (`?lang=` → `localStorage` → browser language). `src/scripts/prefs.ts` handles the EN/ES buttons (`data-set-lang`), swaps `data-i18n-attrs`, and syncs other open tabs through the `storage` event. Any new page must use `Layout.astro` to share them. `/en` and `/es` redirect to `/?lang=…` (`astro.config.mjs`).
- **Sections are Astro components** (`Header`, `Hero`, `Work`, `Lab`, `Rag`, `Stack`, `About` (wraps `Leading`), `Principles`, `Certifications`, `Footer`) receiving slices of the content object. The only React island is `ThemeToggle.tsx`.
- **Theming:** colors are CSS variables in `src/styles/global.css` (`:root` = light, `:root[data-theme='dark']` = dark), exposed to Tailwind through `@theme inline` (`bg-panel`, `text-accent`, `border-line2`, …). Use these tokens, not raw hex. `Layout.astro` has an inline script that sets `data-theme` from `localStorage` before paint (default dark); `ThemeToggle` observes that attribute via `useSyncExternalStore`.
- **Sizing is fluid.** Spacing and type come from tokens in `global.css` (`@theme`): `py-section`, `mt-block`, `gap-stack`, `p-card`, `gap-gutter`, `text-display|hero|h2|lead|h3|sub`, `h-wave`, `size-icon|badge`. They use `clamp()` with `vw` and `svh` so layout compacts on small/short screens. Don't add fixed px paddings/font sizes for layout; page width is `max-w-[1200px]`, anchors offset by `--header-h`.
- Shared look helpers (`.dots`, `.eyebrow`, `.jd-card`, `.jd-fill`, animations) are in `global.css`; `Waveform.astro` generates bar heights in the frontmatter and animates with CSS only.

## Lab demos

- Pages under `src/pages/lab/` (chat: `lab/chat.astro` → `src/components/lab/ChatApp.tsx`). The hero's "Chat with my CV" opens `lab/cv.astro`: the same `ChatApp` with `only="meet"`, locked to that case with no case picker, settings panel or demo dialogs (just the chat, keys, language and theme). It opens on an intro dialog while there's no key (the case's video, how to add a key, and contact buttons; the info button reopens it): there's no shared key on purpose, visitors without one are pointed to a call. It shares the `meet` conversation with the lab chat. `<ClientRouter />` in `Layout.astro` makes same-tab navigation client-side, so module state survives landing ↔ demo navigation and a reload clears it. Scripts that touch the DOM must init on `astro:page-load` (see `Header.astro`) and anything imported by an island must be SSR-safe (see `prefs.ts`).
- Demo state is in-memory nanostores (`src/lab/store.ts`, `src/lab/attachments.ts`): API keys, conversations, drafts. Never persist it (no storage, cookies or URL). Under `astro dev` only, `lab/chat.astro` passes `OPENAI_API_KEY` from `.env` to `ChatApp` (`devKey`) so it starts with a key; builds never read it. Islands that read it must render the initial values while hydrating (`useHydrated` in `ChatApp.tsx`) to avoid hydration mismatches.
- Chat cases live in `src/lab/chat/cases.ts`; each fixes a model per provider (`models: { anthropic, openai }`, matched in tier), effort, max tokens, system prompt and tools (visitors can't pick a model). `PROVIDER` in `cases.ts` sets which provider the chat runs on (OpenAI for now; only its key is asked for). `turn.ts` lazy-loads the provider loop: `anthropic.ts` (Messages API) or `openai-chat.ts` (Responses API, `store: false`, history replayed from memory). Both use the official SDKs with `dangerouslyAllowBrowser` (keys are the visitor's own) and report the same `TurnError` kinds; `ChatSession.api` holds the history in that provider's own format. Client tools are in `tools.ts`, declared once in Anthropic's shape and converted for OpenAI (validate model-supplied input before running). Every case prompt is built from the shared blocks in `cases.ts` (`GUARDRAILS(scope)`, `STYLE`, `CITE`, `LANG`): on-topic only, injected instructions ignored, concise, cites tool sources, replies in the user's latest language. "Meet my AI" is grounded by `get_profile_section`/`search_profile` over `profile.ts`: the CV as data in `cv.ts` (transcribed from the private CV repo, one id per item), portfolio copy read from `content.en`, and `notes` that aren't in the CV. CV citations link to the PDF in `src/assets/cv/` with `#cv=<item id>`; in the chat they open `CvViewer.tsx`, the CV rendered with the cited items highlighted. When the CV changes, update both `cv.ts` and the PDF. Its `show_contact_options` tool draws meeting / email / LinkedIn / GitHub buttons at the end of the turn (`ContactActions` in `ChatApp.tsx`; links in `src/lab/chat/contact.ts`). The meeting button opens the Google Calendar booking page (it can't be prefilled), with a hint to say what the meeting is about in its form. It says "soon" while `CONTACT.booking` is null. The "Order assistant" runs on a made-up diner in `order.ts` (bilingual menu with option groups and per-option allergens, sold-out items, `applyOps` validating and pricing every change): the model only calls `search_menu` / `show_menu` / `update_order` / `place_order`, and the order lives in `ChatSession.order` (tools get the turn's session as `run`'s third argument; a retry restores the order the turn started with). Required option groups without a `default` (bowl base, protein and dressing; soda flavor) make `update_order` fail until the customer picks, so the model asks instead of guessing. These tools take `lang` (the customer's language, `en`/`es`): names come back in it and the order and menu cards render in it, whatever the page language. `OrderCard` in `ChatApp.tsx` shows the order once, after the last turn that changed it; its Place order button sends a confirmation message, so the model still calls `place_order`. `show_menu` with a category or dishes draws `MenuCard` in the log (tapping a dish fills the composer); with neither, the whole menu opens once in a view-only dialog (opened from the turn's `update` callback) and the log keeps a button to reopen it. It takes only text and voice (`attachments: false` hides the attach button). The "Auto insurance assistant" runs on a made-up account in `insurance.ts` (one policy with no end date on a red 2022 Mazda 3, coverages with deductibles, incident types mapped to a coverage or an exclusion). It first asks the customer's name and `set_customer_name` puts the account in it (the other insurance tools fail until then); then `get_policy` / `check_coverage` answer about it, `request_photo` / `request_document` draw an upload button that offers sample files (`src/assets/lab/insurance/`: the insured car damaged, another car, and a body shop invoice PDF made for the demo) or the visitor's own, `check_photo` takes what the model sees in the photo of the current turn (color, body, make, damaged parts from a fixed list so the card can translate them) and the code decides match / mismatch / unclear against the insured car, and `file_claim` only files with a matching photo (not for theft), a covered incident, a date between the policy start and today and a description. The damage value is optional and can come later, but only through `attach_invoice`, backed by a PDF: the case sets `pdf: { maxPages: 5, maxMB: 10 }`, so `src/lab/pdf.ts` (pdf.js, lazy-loaded) refuses bigger or longer PDFs when they are attached and renders the pages as JPEGs; only page 1 goes with the message, `check_document` classifies it (invoice, quote or other: other is discarded) and only then returns the other pages as tool images, and tool images are dropped from the history once their turn ends (`PAGES_DROPPED` in `turn.ts`). The accepted document becomes the annex, and the declared amount must be within $1 of the total the model reads on it, with the insured plate. The name, claims and latest photo check live in `ChatSession.claims` (restored on retry like the order) and are always "in review" (`get_claim_status`). The policy opens once in a dialog when `get_policy` finishes (like the full menu) and leaves a "See the policy" button; `AttachRequest` and `ClaimCard` in `ChatApp.tsx` render at the end of their turn, in the tool's `lang`; claim cards find their claim by the `CLM-…` number in the tool's result label. Images the visitor sends show in the log as previews and other files (PDFs) as download links (user items keep `SentFile`s with a data URL). Voice transcription is in `openai.ts`. The "Document intelligence" case (`docs: { maxFiles: 5, maxPages: 20, maxMB: 20, effortMany }`) runs on Luna at `low` effort with an empty Knowledge Base (shown only: sending is refused before any request), `medium` with one document and `high` with more (`caseEffort`, read per turn by both providers and shown in the UI). It answers only from a **Knowledge Base**: a box of 5 slots above the composer (`KnowledgeBase` in `ChatApp.tsx`) that replaces the attach button and suggestions; it starts open and folds into one line (documents as chips, Show/Hide) once the first message is sent. Slots take PDFs and images and fill straight into `ChatSession.docs` (ids `d1`… from `docSeq`, never reused; removable; edits are blocked while a turn runs, since the turn works on a copy of the session; "Clear conversation" keeps them, switching cases doesn't). `src/lab/kb.ts` reads each file in the browser: PDFs through `indexPdf` in `src/lab/pdf.ts` (pdf.js text layer → passages of ~600–1000 chars, never across pages, each with its line boxes in PDF units), images downscaled to a JPEG. Files never go to the provider: every message carries a `kbNote` (`UserInput.context`) listing the Knowledge Base as it is now, and sending with it empty shows the `docNone` notice without a request. The model reads it through `list_documents` / `search_documents` (BM25 over PDF passages in `src/lab/chat/docs.ts`; the prompt makes it search in the document's language) / `read_pages` (≤3 pages, ~12k chars) / `view_page` (an image, or a PDF page as an image; dropped after the turn like other tool images). Its prompt is strict: only what it read or saw in the Knowledge Base, no general knowledge, no identifying people in images. Every passage comes back with a source whose url is `<origin>/lab/chat#doc=d2-p5-c3` (a whole page or image: `d2-p5`); The prompt asks for one link per passage used (up to 12) and `foldSources` in `ChatApp.tsx` shows links with the same label (file and page) once. `docLinkId` turns those links into clicks that open `DocViewer.tsx`, which renders the page with pdf.js and highlights every passage the answer cites (images are outlined), or says the document was removed. A "Try a sample contract" link in the empty box adds `src/assets/lab/documents/sample-contract.pdf` (a made-up services agreement, generated as a text-layer PDF). Chat copy is in `src/i18n/chat.ts`; `{p}`/`{m}` in it are replaced with the provider and model names.
- Errors are assistant messages (`notice` items with a code), typed out and ending in a fix button (`FIXES` in `ChatApp.tsx`). OpenAI's error responses carry no CORS header, so in the browser a rejected key surfaces as a connection error (`unreadable`), not a 401.
- The chat header opens two dialogs: **Watch demo** has a case picker and plays `video` from the case (`{ src, captions }`, WebVTT captions required; without it a placeholder shows); **How I’d build it** shows one general architecture diagram and explanation (placeholder for now). Both size their 16:9 frame from the viewport height so the dialog never scrolls. On phones both buttons live in the settings sheet.

## Images

- AWS icons are official SVGs in `src/assets/aws/` (sourced from the JuanDLCH profile repo; `sns.svg` from the design). `Stack.astro` resolves them via `import.meta.glob` to hashed URLs. Run `pnpm optimize:svg` (SVGO, `svgo.config.mjs`) after adding any SVG.
- `vite.build.assetsInlineLimit` is 0 on purpose: otherwise small images are inlined as `data:` URIs and `loading="lazy"` does nothing. Below-the-fold images must use `loading="lazy" decoding="async"` with explicit width/height.
- Raster images (certification badges, hero photo) go in `src/assets/` and render with Astro's `<Image>`/`<Picture>` (sharp, webp/avif); never in `public/`.

## Development rules

- `main` is protected: no direct pushes. Work on short-lived branches named `<type>/<slug>` (e.g. `feat/hero-photo`), open a PR, and squash-merge once the `verify` CI check (`.github/workflows/ci.yml`: lint, format check, `astro check`, build) passes. The PR title becomes the commit message, so it must be a Conventional Commit. Branches are deleted on merge.
- Commits follow Conventional Commits (`commitlint.config.js`): `feat`, `fix`, `content` (copy changes), `style`, `refactor`, `perf`, `docs`, `test`, `build`, `ci`, `chore`, `revert`. English, imperative, header ≤ 72 chars. One logical change per commit.
- Husky hooks: `pre-commit` runs lint-staged (ESLint + Prettier on staged files); `commit-msg` runs commitlint. Don't bypass with `--no-verify`.
- Colors come from theme tokens (`text-accent`), never raw hex. New copy goes in `src/i18n/content.ts` for both languages. No `any`.
- Dependabot ignores TypeScript major bumps (see TypeScript note above).
